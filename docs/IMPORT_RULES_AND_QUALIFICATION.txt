===============================================================================
1. PURPOSE AND SCOPE
===============================================================================

This document defines the import and interchange contract implemented by the
current Rust application. It is intended to answer, without requiring PR
history:

- which import/interchange mechanisms exist now;
- which semantic records each mechanism can create or update;
- the identity, ownership, reference, validation, preview, transaction,
  persistence, and presentation rules an importer must obey;
- which capabilities have repeatable qualification evidence;
- which capabilities are implemented but only partially qualified;
- which capabilities are partial, planned, not implemented, or out of scope;
- how current Groovy/model scripting and ReqIF adapters join the shared Rust
  construction architecture, and how the XMI adapter follows it while a future
  SysML v2 adapter must do the same.

This is not a compatibility certification. Terms such as "CATIA-style" or
"Cameo-style" describe configurable mapping approaches only. They do not mean
release-specific CATIA, Cameo, or 3DEXPERIENCE compatibility unless a separate
release-specific qualification exists.

This document describes current main. Planned work is labeled explicitly and
must not be read as an implementation claim.

===============================================================================
2. STATUS TERMINOLOGY
===============================================================================

QUALIFIED
  Implemented, backed by repeatable automated evidence for the claimed
  boundary, with persistence/reimport and relevant regression coverage where
  those concerns apply.

IMPLEMENTED / PARTIALLY QUALIFIED
  A real code path exists, but automated evidence is not complete for every
  row, field, variant, or matrix cell that could be implied by the broader
  capability name.

PARTIAL
  Material parts of the concept exist, but important semantics or lifecycle
  behavior remain unavailable or deliberately bounded.

PLANNED
  Intended future work. No current implementation is implied.

NOT IMPLEMENTED
  No current Rust implementation for the claimed adapter/capability boundary.

OUT OF SCOPE
  Deliberately excluded from the stated contract.

NOT SUPPORTED
  The product does not currently read or operate on that source format or
  native file type.

A capability is not QUALIFIED merely because an enum variant or parser branch
exists.

4. CORE CONSTRUCTION ARCHITECTURE
===============================================================================

All bulk/import adapters must converge on the shared Rust construction path.
Conceptually:

  external source
       |
       v
  parser / adapter
       |
       v
  normalized mapped records
       |
       v
  ModelBuildPlan
       |
       v
  resolve references against existing + plan-local authored state
       |
       v
  construct and validate the complete candidate
       |
       v
  preview / diagnostics
       |
       v
  one atomic apply

ModelBuildPlan is the shared construction authority. Its current operation set
covers ordinary semantic elements and relationships, Connectors and ItemFlows,
Activity and State Machine authored records, Sequence authored records,
Parametric authored updates/Bindings, diagram/presentation operations used by
native/portable paths, and portable-state restoration.

ActivityRepository and BehaviorRepository are established native semantic
stores, not importer-specific repositories. When specialized authored records
participate, the complete candidate path validates Project plus the relevant
native repositories together before committing them.

The following importer architectures are forbidden:

- direct spreadsheet -> Project mutation;
- direct importer -> SQLite mutation;
- row-by-row semantic commits;
- map-by-map early commits solely so later rows can resolve references;
- importer-specific semantic repositories that bypass the native stores;
- importer-specific semantic validation that disagrees with model-core or the
  established Activity/Behavior validation rules;
- a second execution/evaluation path invented only for imported content.

Ordered spreadsheet MapGroups may make records from earlier maps available to
later maps through plan-local identity. That is not an early commit.

5. GLOBAL IDENTITY CONTRACT
===============================================================================

The following identities are distinct:

Internal stable ID
  Authoritative repository identity. Common Project records use stable typed
  IDs such as ElementId and RelationshipId. Activity/Behavior nested records
  use their own stable native IDs.

External ID
  Import/interchange-facing authored identity. Spreadsheet semantics persist
  it with a source namespace.

Source namespace
  Separates identity domains. The canonical mapped key is conceptually:

    source namespace + External ID

  and is the strongest spreadsheet reimport identity.

Requirement ID
  Controlled human-facing Requirement identifier. It is deliberately separate
  from the internal stable ID and External ID.

Qualified name
  Deterministic semantic path used for exact resolution where supported. It is
  not a substitute for stable External ID when durable reimport identity is
  available.

Display name
  Human-facing name. It is not permanent identity. Some current spreadsheet
  resolution paths permit exact-name fallback only when the match is unique;
  durable integrations should use External ID or exact qualified names.

Plan-local reference
  A reference to a record created earlier in the same uncommitted build plan or
  ordered MapGroup.

The following are never semantic identity:

- spreadsheet row number;
- worksheet position;
- diagram pixel position;
- presentation ID standing in for the semantic object;
- fuzzy name similarity.

Duplicate and ambiguity rules:

- duplicate namespaced External ID in the same identity domain -> BLOCKED;
- same stable identity with incompatible semantic kind -> BLOCKED;
- ambiguous fallback resolution -> BLOCKED;
- unresolved required reference -> BLOCKED;
- unique exact fallback -> may resolve where that adapter explicitly supports
  the fallback;
- no importer may guess among multiple matches.

For relationships, current spreadsheet mappings support External ID identity
and controlled semantic fallback policies such as kind/source/target and
association-end-aware identity. External ID remains the preferred durable
reimport identity.

===============================================================================
6. OWNERSHIP, CONTEXT, AND PRESENTATION
===============================================================================

These are separate concepts:

semantic ownership
  The native containment/ownership relation for a semantic object.

diagram ownership
  The semantic owner of a diagram definition.

diagram semantic context
  The Block/classifier/namespace or other semantic context represented by the
  diagram, where the family has one.

presentation placement
  A graphical appearance of an existing semantic element/relationship on a
  particular diagram.

Global rule:

  presenting an element on a diagram must never silently reparent it

A semantic element may appear on zero, one, or many compatible diagrams. A
semantic relationship may likewise have zero, one, or many graphical edges.
Deleting a presentation does not implicitly delete the semantic object.

Imports must not create loose root-level semantic objects as a fallback for
unresolved legal ownership. If ownership is required and cannot be resolved,
the row/import is BLOCKED unless a specific native semantic rule defines a
single deterministic legal owner.

Examples of current owner/context constraints include:

- Parameters are owned by Operations;
- typed properties and Ports require legal classifier/constraint ownership;
- Connectors require a structured classifier context;
- behavior records require the native Activity/State Machine/Interaction
  context expected by their repository;
- package/namespace relationships obey native namespace ownership rules.

===============================================================================
7. SEMANTIC OBJECTS ARE NOT PRESENTATIONS
===============================================================================

The following equivalences are invalid:

  semantic element       != diagram node
  semantic relationship  != diagram edge

Spreadsheet semantic import through the current PR49 baseline does not create
or populate diagrams. The generic ModelBuildPlan has diagram/presentation
operations and portable JSON restores authored presentation state, but the
spreadsheet mapping path deliberately stops at semantics.

All-nine-family spreadsheet-driven diagram construction remains PLANNED / NOT
YET IMPLEMENTED on this baseline. Do not report semantic import as diagram
import.

===============================================================================
8. REFERENCE RESOLUTION CONTRACT
===============================================================================

Current adapters use the following reference forms where applicable:

- source namespace + External ID;
- plan-local External ID/reference;
- exact qualified name;
- configured spreadsheet identification property;
- Requirement ID for Requirement-oriented resolution;
- exact name fallback in specific current mappings only when unique.

There is no fuzzy matching.

Required resolution result:

  unique legal match     -> resolve
  no match               -> BLOCKED
  multiple matches       -> BLOCKED
  wrong semantic kind    -> BLOCKED

Missing endpoints, types, owners, Signals, Connectors, Lifelines, Regions,
Parameters, or other references must not be invented merely to make an import
succeed. A missing object may resolve plan-locally only if the mapping actually
creates that object earlier in the same complete plan.

===============================================================================
9. NATIVE VALIDATION CONTRACT
===============================================================================

Imported authored content must pass the same native Rust semantic validation as
manually authored content. Importers must not weaken validation to accept a
source file.

Current validation coverage applies, at the represented boundary, to:

- legal ownership and namespace rules;
- element/classifier kind constraints;
- type compatibility;
- multiplicity where represented;
- property and Port ownership/type/conjugation rules;
- relationship endpoint kind, direction, ownership, and duplicate rules;
- Association end semantics;
- Connector context/topology and ConnectorEnd paths;
- ItemFlow Connector-relative topology and conveyed classifier references;
- Requirement traceability relationship semantics;
- Use Case Include/Extend and namespace relationship semantics;
- Operation/Parameter/Reception/Signal compatibility;
- Activity authored semantics;
- State Machine Region/Vertex/Transition/trigger semantics;
- Sequence Interaction/Lifeline/Occurrence/Message/fragment semantics;
- Parametric Binding endpoints and engineering metadata represented by the
  native model;
- QuantityKind/Unit references and finite conversion metadata where PR49 maps
  those fields.

Validation claims apply only where the underlying native model represents the
semantic concept. An importer must not invent missing semantics.

===============================================================================
10. PREVIEW CONTRACT
===============================================================================

Spreadsheet preview uses the following classifications:

  CREATE
  UPDATE
  NO_CHANGE
  WARNING
  BLOCKED

Preview performs the work needed to determine whether the candidate can be
accepted, including source parsing, column mapping/normalization, identity and
reference resolution, build-plan construction, candidate validation, and
structured diagnostics.

Preview requirement:

  ZERO persistent mutation

A preview is not permitted to mutate Project, ActivityRepository,
BehaviorRepository, native persistence, or authored diagram state merely to
resolve later rows.

===============================================================================
11. TRANSACTION AND ROLLBACK CONTRACT
===============================================================================

Absolute rule:

  valid complete import     -> one logical commit
  blocking failure anywhere -> zero commit

For spreadsheet imports:

  entire ordered MapGroup = one logical transaction

A late blocking error must leave no earlier planned semantic hierarchy,
relationship, Connector, ItemFlow, behavior record, Sequence record, Parametric
Binding, or other authored record committed from that MapGroup.

Current spreadsheet diagram construction is not implemented. When presentation
construction is added later, presentations must join the same candidate/rollback
contract rather than commit separately before semantic validation succeeds.

No partial placeholder hierarchy is an acceptable rollback strategy.

===============================================================================
12. REIMPORT AND RECONCILIATION RULES
===============================================================================

Required current behavior:

  same stable identity + identical authored data
      -> NO_CHANGE

  same stable identity + valid changed authored data
      -> UPDATE

  same stable identity + incompatible semantic kind
      -> BLOCKED

  duplicate External ID in same source identity domain
      -> BLOCKED

  ambiguous fallback identity
      -> BLOCKED

A display-name change must not create a duplicate semantic object when the
source namespace + External ID remains stable.

Deletion/reconciliation policy:

  STATUS: NOT IMPLEMENTED / PLANNED

Current spreadsheet import is create/update/no-change oriented. Absence of a row
from a later workbook does not authorize deletion unless a future explicit
reconciliation contract says so.

13. SPREADSHEET MAPPING CONTRACT
===============================================================================

The spreadsheet importer follows a configurable CATIA/Cameo-style mapping
philosophy:

  physical workbook structure != semantic model structure

Current mapping structures support:

- CSV and XLSX source files;
- arbitrary business-facing column names mapped to controlled semantic
  properties;
- arbitrary worksheet names for XLSX;
- configurable one-based header row;
- stable target scope by ElementId;
- TargetOnly versus TargetRecursive search scope;
- ExternalId, Name, or RequirementId identification modes;
- source namespace and mapping version;
- ordered MapGroups;
- explicit semantic ElementKind for ordinary maps;
- controlled RelationshipKind mapping for relationship maps;
- controlled BehaviorKind rows for Activity/State Machine/Sequence/Parametric
  specialized authored records;
- owner, type, relationship endpoint, Connector, ItemFlow, behavior, Sequence,
  and Parametric semantic properties according to their qualified scopes.

The mapping profile is allowed to translate business headers to semantic fields.
Rust field names are not required to appear in the workbook.

Current format parser dispatch is explicit:

  .csv  -> supported
  .xlsx -> supported
  .xls  -> not implemented

17. PORT, CONNECTOR, AND ITEMFLOW RULES
===============================================================================

ProxyPort / FullPort
--------------------

Current spreadsheet import is QUALIFIED for native ProxyPort and FullPort
semantics, including:

- legal semantic owner;
- compatible modeled type;
- multiplicity;
- conjugation where the native kind supports it;
- documentation and visibility;
- source namespace + External ID identity;
- plan-local owner/type resolution;
- create/update/no-change reimport;
- native persistence and portable JSON round trip.

An importer must not synthesize a compatible type merely because the workbook
omits one. Required type resolution failure is BLOCKED.

Connector / ConnectorEnd
------------------------

Current spreadsheet import is QUALIFIED for native Connectors and ConnectorEnds
with:

- structured classifier Connector context;
- Assembly/Delegation Connector kind;
- role-only endpoints;
- boundary-Port endpoints;
- nested Port endpoints;
- nested property paths;
- multi-level structural paths;
- plan-local structural records;
- create/update/no-change and atomic rollback;
- native topology validation.

Endpoint paths are resolved scope-by-scope. An ambiguous or illegal segment is
BLOCKED rather than guessed.

ItemFlow
--------

Current spreadsheet import is QUALIFIED for native ItemFlow semantics with:

- referenced native Connector;
- source and target ConnectorEnds;
- Connector-relative direction/topology;
- one or more conveyed classifier references where represented;
- plan-local Connector/classifier resolution;
- stable identity and update/no-change reimport;
- native persistence and portable interchange.

Connector, ConnectorEnd, and ItemFlow import is semantic only. Spreadsheet
import does not create corresponding IBD edges, paths, labels, waypoints, or
layout on this baseline.

18. REQUIREMENTS AND TRACEABILITY RULES
===============================================================================

The current spreadsheet importer distinguishes:

- internal stable ID;
- source namespace + External ID;
- Requirement ID;
- Requirement name/text.

Requirement ID is a controlled human-facing identifier and may participate in
Requirement-oriented exact resolution. It is not the same thing as External ID
or the internal stable ID.

Qualified traceability relationships and current direction are the native
source -> target semantics encoded by the corresponding RelationshipKind:

- DeriveRequirement / deriveReqt;
- Satisfy;
- Verify;
- Refine;
- Trace;
- Copy;
- Allocate (a general allocation relationship; not a verification result).

Critical rule:

  Verify relationship != Requirement verified status

Importing a Verify relationship creates traceability only. It does not create
test evidence, execute a TestCase, infer a verification conclusion, or silently
change Requirement lifecycle/status fields.

19. ACTIVITY IMPORT AND RUNTIME COMPATIBILITY
===============================================================================

Semantic spreadsheet import status: QUALIFIED
Runtime participation: QUALIFIED at the represented PR31 execution boundary,
with explicit partial/unsupported structured semantics described below.

Imported Activity content can include Activities, partitions, structured
activity nodes, control nodes, actions, object nodes, ActivityParameterNodes,
pins, ControlFlows, ObjectFlows, guards, weights, selection/transformation
metadata, and interrupting-region references represented by the native model.

Qualified action import includes:

- OpaqueAction;
- CallBehaviorAction;
- CallOperationAction;
- SendSignalAction;
- AcceptEventAction;
- AcceptTimeEventAction.

Runtime distinctions:

- imported Activities execute through the existing native Activity runtime;
- OpaqueAction execution remains bounded to supported pure-expression semantics;
  arbitrary script/statements are not enabled by import;
- structured containers execute only the native semantics represented by the
  current model/runtime;
- missing ExpansionRegion/ConditionalNode semantics are not invented by the
  importer.

Importable/authored is not equivalent to executable for every future UML/SysML
Activity construct.

20. STATE MACHINE IMPORT AND RUNTIME COMPATIBILITY
===============================================================================

Semantic spreadsheet import status: QUALIFIED
Runtime participation: QUALIFIED for the supported PR32 execution subset;
PARTIAL across all imported pseudostate variants.

REQIF QUALIFIED CONTRACT (PR52)
===============================================================================

ReqIF is a requirements interchange adapter, not a second model authority.

Supported exchange boundary:

- `.reqif` XML and compressed `.reqifz` containers;
- ReqIF header, datatypes, SpecTypes, SpecObjects, Specifications/hierarchy,
  SpecRelations, and typed attribute values;
- STRING, XHTML, BOOLEAN, INTEGER, REAL, DATE, and ENUMERATION values;
- configurable SpecObject -> native Requirement/TestCase mapping;
- configurable SpecRelation -> supported native traceability relationship mapping;
- configurable attribute -> Requirement ID, Requirement Text, Name, and
  Documentation mapping;
- unmapped ReqIF attributes and original XHTML retained in ReqIF exchange
  metadata so mapped native content does not silently destroy supplier data;
- stable semantic identity is `(source namespace, ReqIF IDENTIFIER)`;
- identical reimport resolves to NO_CHANGE rather than duplication;
- additive synchronization never removes native content;
- authoritative ReqIF synchronization may remove only records proven to belong
  to that same ReqIF source namespace and absent from the new exchange;
- preview reports CREATE / UPDATE / NO_CHANGE / REMOVE / BLOCKED before apply;
- parse, reference, ownership, mapping, and semantic errors block the complete
  candidate; valid application is atomic;
- ReqIF source configuration and exchange fidelity metadata survive `.smproj`;
- deterministic `.reqif` export and `.reqifz` packaging are supported for a
  selected Model/Package scope;
- imported Requirements/TestCases are ordinary native model elements and
  imported traceability is ordinary native relationships, so existing
  requirements diagrams, editing, persistence, spreadsheet/Groovy paths, and
  execution architecture remain authoritative.

ReqIF does not imply XMI, SysML v2, CATIA native-file compatibility, or a
profile/stereotype framework. Those remain separate future scopes.
